# ระบบติดตามกิจกรรมจัดซื้อของ Buyer — Module 1 (Vendor Sourcing)

ระบบติดตามกิจกรรมการจัดซื้อจัดจ้าง CAPEX / OPEX บน **Google Apps Script + Google Sheets**
พัฒนาตาม SPEC Module 1 (ค้นหาและเปรียบเทียบ Vendor) โดยวางโครงสร้างข้อมูลของ Module 2–6 ไว้แล้ว
เพื่อไม่ต้อง migrate ข้อมูลเมื่อพัฒนาโมดูลถัดไป

## 2. โครงสร้าง `src/` แปลงเป็นอะไรใน Apps Script

**Apps Script ไม่มีโฟลเดอร์** โฟลเดอร์ใน repo นี้มีไว้ให้คนอ่านโค้ด — ตอน `clasp push`
clasp จะเอา path มาเป็น *ชื่อไฟล์* ที่มี `/` อยู่ในชื่อ (ตัดเฉพาะนามสกุลสุดท้ายออก)

| บนดิสก์ | ชื่อไฟล์ใน Apps Script | ชนิด |
|---|---|---|
| `src/server/Auth.js` | `server/Auth` | `.gs` |
| `src/server/Api.js` | `server/Api` | `.gs` |
| `src/client/Index.html` | `client/Index` | `.html` |
| `src/client/App.js.html` | `client/App.js` | `.html` (ตั้งชื่อแบบนี้เพื่อให้ editor ไฮไลต์ JS) |
| `src/client/views/MyCases.html` | `client/views/MyCases` | `.html` |

สองอย่างที่ตามมา:

- **ไฟล์ `.gs` ทุกไฟล์ใช้ global scope ร่วมกัน** ไม่ว่าจะอยู่ "โฟลเดอร์" ไหน `Api.js` จึงเรียก
  `CaseService.create()` ได้โดยไม่ต้อง import — และเป็นเหตุผลที่ test harness โหลดทุกไฟล์เข้า
  vm context เดียวกัน
- **ไฟล์ `.html` ต้องอ้างด้วยชื่อเต็ม** เช่น `include('client/views/MyCases')`

### ⚠️ กับดัก: `rootDir` ต้องไม่หาย

บรรทัด `"rootDir": "src"` ใน `.clasp.json` คือสิ่งที่ทำให้ `src` ไม่ติดมาในชื่อไฟล์
`clasp create` จะเขียน `.clasp.json` ใหม่ทับ — ถ้า `rootDir` หลุดไป ชื่อไฟล์จะกลายเป็น
`src/server/Auth` และ `src/client/Index`

repo นี้มี `.clasp.json` อยู่แล้ว `clasp create` จึงจะ **refuse** (`Project file already exists`)
ซึ่งเป็นเรื่องดี — ให้สร้างโปรเจกต์จากหน้าเว็บแล้วแก้เฉพาะ `scriptId` ตามขั้นตอนข้างล่าง

> ระบบทนต่อกรณีนี้อยู่แล้ว (`resolveHtmlName()` ใน `Main.js` จะไล่ลองชื่อสำรองให้)
> แต่ `verifyDeployment()` จะขึ้นคำเตือนเพื่อให้กลับไปแก้ config ให้ถูก

**วิธีเช็คว่า push ถูก:** ใน Apps Script editor ต้องเห็นชื่อไฟล์ขึ้นต้นด้วย `server/` และ `client/`
ถ้าเห็น `src/server/` แปลว่า `rootDir` หายไป

## 3. การติดตั้งครั้งแรก

ต้องมี [Node.js](https://nodejs.org/) และ [clasp](https://github.com/google/clasp) (`npm i -g @google/clasp`)

```bash
# 1. เข้าสู่ระบบ Google ด้วยบัญชีที่จะเป็น "เจ้าของระบบ"
clasp login

# 2. สร้างโปรเจกต์เปล่าที่ https://script.google.com → New project
#    แล้วคัดลอก Script ID จาก Project Settings
#    เปิด .clasp.json แก้เฉพาะบรรทัด scriptId — อย่าแตะ rootDir
#    (อย่าใช้ clasp create เพราะจะเขียนทับ .clasp.json ทั้งไฟล์)

# 3. อัปโหลดโค้ดขึ้น Apps Script (37 ไฟล์: server 26 + client 11)
clasp push

# 4. เปิดโปรเจกต์ในเบราว์เซอร์
clasp open
```

จากนั้นในหน้าต่าง Apps Script:

1. **รันฟังก์ชัน `setup()` หนึ่งครั้ง** (เลือกจาก dropdown แล้วกด Run แล้วกดอนุญาตสิทธิ์)
   - ระบบจะสร้างไฟล์ Google Sheets ชื่อ `Buyer Procurement Activity — DB` ให้
   - สร้างชีตครบทั้ง 14 ตาราง ใส่หัวคอลัมน์ และใส่ข้อมูล Config เริ่มต้น
   - เพิ่มบัญชีที่รัน `setup()` ลงในชีต `Users` ด้วยบทบาท `ADMIN`
   - ดู URL ของไฟล์ DB ได้จาก Execution log
2. **เปิดไฟล์ DB แล้วตั้งค่าในชีต `Config_Settings`** (ดูหัวข้อ "การตั้งค่า")
3. **เพิ่มผู้ใช้ในชีต `Users`** (ดูหัวข้อ "ผู้ใช้และสิทธิ์")
4. **รันฟังก์ชัน `installTriggers()` หนึ่งครั้ง** เพื่อตั้งอีเมลแจ้งเตือนรายวัน
5. **Deploy เป็น Web app** — ดูหัวข้อย่อย "การ Deploy" ด้านล่าง
6. **รันฟังก์ชัน `verifyDeployment()`** แล้วอ่าน Execution log — จะได้ checklist 12 ข้อ
   บอกว่ามีอะไรยังไม่เรียบร้อย (ดูหัวข้อ "ตรวจความพร้อมหลัง deploy")

> ⚠️ **ห้ามแชร์ไฟล์ DB ให้ผู้ใช้ทั่วไป** ระบบถูกออกแบบให้ผู้ใช้เข้าถึงข้อมูลผ่านหน้าเว็บเท่านั้น
> ไฟล์ DB ควรแชร์เฉพาะผู้ดูแลระบบ

### การ Deploy (สำคัญต่อความปลอดภัย)

`Deploy` → `New deployment` → เลือก type `Web app` แล้วตั้งค่า:

| ตัวเลือก | ค่าที่ต้องใช้ | เหตุผล |
|---|---|---|
| Execute as | **Me (บัญชีเจ้าของระบบ)** | ผู้ใช้เข้าถึงข้อมูลผ่านโค้ดเท่านั้น ไม่ต้องแชร์ไฟล์ DB ให้ใคร |
| Who has access | **Anyone within (โดเมนบริษัท)** | จำกัดเฉพาะคนในองค์กร |

ระบบจะอ่านตัวตนผู้ใช้จาก `Session.getActiveUser().getEmail()` แล้ว**ตรวจสิทธิ์จากชีต `Users` ใหม่ทุกครั้ง
ที่เรียก API ฝั่ง server** ผู้ที่ไม่มีในชีต `Users` หรือมี `Is_Active = FALSE` จะเห็นหน้า "ไม่มีสิทธิ์เข้าใช้งาน"

ทุกครั้งที่แก้โค้ดแล้ว `clasp push` ต้อง `Deploy` → `Manage deployments` → แก้ deployment เดิมเป็น
`New version` ด้วย ผู้ใช้จึงจะเห็นของใหม่

## 4. ตรวจความพร้อมหลัง deploy

รัน `verifyDeployment()` จาก Apps Script editor แล้วเปิด Execution log จะได้ checklist แบบนี้

```
===== ตรวจความพร้อมของระบบ =====
[ ผ่าน ]   1. ไฟล์ฐานข้อมูล
[ ผ่าน ]   2. ชีตและหัวคอลัมน์ครบตาม Schema
[ ผ่าน ]   3. ไฟล์หน้าเว็บ (ตรวจชื่อที่ clasp ตั้งให้จริง)
[ ผ่าน ]   4. ค่าตั้งค่าหลัก
[ เตือน ]  5. โฟลเดอร์หลักใน Google Drive
             ยังไม่ได้ตั้ง DRIVE_ROOT_FOLDER_ID — ระบบจะสร้างโฟลเดอร์ให้เองเมื่อเปิด Case แรก
[ ผ่าน ]   6. รายการ dropdown ที่จำเป็น
[ เตือน ]  7. ข้อมูลตัวอย่างที่ต้องแทนที่ด้วยของบริษัท
             ยังเป็นค่าตัวอย่างที่ระบบใส่ให้: DEPARTMENT (OPS, MKT, FIN) · ...
[ ผ่าน ]   8. สถานะงานและเส้นทางของ Module 1
[ ผ่าน ]   9. ผู้ใช้งาน
[ เตือน ] 10. อีเมลแจ้งเตือนรายวัน
             ยังไม่ได้ติดตั้ง trigger — กรุณารัน installTriggers()
[ ผ่าน ]  11. การ Deploy เป็น Web app
[ ผ่าน ]  12. โควตาอีเมลคงเหลือวันนี้

สรุป: ผ่าน 9 · เตือน 3 · ไม่ผ่าน 0
ใช้งานได้ แต่มีข้อเตือนที่ควรแก้ก่อนเปิดให้ทั้งฝ่ายใช้
================================
```

| ระดับ | ความหมาย |
|---|---|
| **ไม่ผ่าน** | ระบบใช้งานไม่ได้ ต้องแก้ก่อน |
| **เตือน** | ใช้งานได้ แต่ยังไม่ควรเปิดให้ทั้งฝ่ายใช้ |
| **ผ่าน** | เรียบร้อย |

ข้อ 3 และ 7 คือข้อที่ควรดูให้ดีที่สุด

- **ข้อ 3** เป็นสิ่งเดียวที่ชุดทดสอบบน Node พิสูจน์แทนไม่ได้ — มันตรวจว่า clasp ตั้งชื่อไฟล์ HTML
  ทั้ง 11 ไฟล์ตรงกับที่โค้ดเรียกหาจริงหรือไม่ **ก่อน**ที่จะมีผู้ใช้คนไหนเปิดหน้าเว็บแล้วเจอจอว่าง
- **ข้อ 7** กันไม่ให้เปิดใช้งานจริงทั้งที่ dropdown ยังเป็นค่าตัวอย่าง (`OPS / MKT / FIN`)
  ที่ `setup()` ใส่ให้เพื่อให้ระบบเริ่มทำงานได้เท่านั้น

ผู้ดูแลระบบเรียกจากในแอปก็ได้ผ่าน `api_verifyDeployment()` (เฉพาะบทบาท ADMIN)

## 5. การอัปเดตหลังจากนี้

```bash
clasp push                 # อัปโหลดโค้ด
# แล้วจาก Apps Script editor:
#   setup()               ถ้ามีการเพิ่มตาราง/คอลัมน์ใน Schema.js
#   verifyDeployment()    ทุกครั้ง เพื่อยืนยันว่ายังเรียบร้อยดี
```

`setup()` ปลอดภัยที่จะรันซ้ำเสมอ: จะสร้างเฉพาะชีตที่ยังไม่มี **เพิ่มคอลัมน์ใหม่ต่อท้ายชีตเดิม
โดยไม่ย้ายหรือลบคอลัมน์ใด** และใส่ข้อมูล Config เฉพาะแถวที่ยังไม่มี — ค่าที่ผู้ดูแลระบบแก้ไว้จะไม่ถูกเขียนทับ

## 6. การตั้งค่า (ชีต `Config_Settings`)

| Key | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `MIN_QUOTES` | `3` | จำนวนใบเสนอราคาขั้นต่ำก่อนปิดขั้นตอนหา Vendor |
| `REQUIRE_ALL_ITEMS_PRICED` | `TRUE` | ผู้ขายต้องเสนอราคาครบทุก item จึงจะนับเป็นใบที่ใช้ได้ |
| `BUYER_CAN_VIEW_ALL` | `TRUE` | Buyer เห็นงานของคนอื่นแบบอ่านอย่างเดียว |
| `SPECIAL_REQUIRES_EXCEPTION` | `TRUE` | งาน Method = SPECIAL ต้องขอยกเว้นเหมือนงานปกติเมื่อใบเสนอราคาไม่ครบ |
| `DRIVE_ROOT_FOLDER_ID` | (ว่าง) | โฟลเดอร์หลักที่เก็บโฟลเดอร์ของแต่ละงาน — ถ้าเว้นว่าง ระบบจะสร้างให้ครั้งแรกที่ใช้งานแล้วเขียนค่ากลับมาที่นี่ |
| `REMINDER_HOUR` | `8` | ชั่วโมงที่ส่งอีเมลสรุปรายวัน (ต้องรัน `installTriggers()` ใหม่หลังแก้) |
| `REMINDER_DAYS_AHEAD` | `1` | เตือนสิ่งที่ต้องทำต่อที่ครบกำหนดภายในกี่วันข้างหน้า |
| `APP_TIMEZONE` | `Asia/Bangkok` | โซนเวลาของระบบ |

**ชีต `Config_Lists`** เก็บทุก dropdown ในระบบ (`List_Name`, `Code`, `Label_TH`, `Parent_Code`, `Sort_Order`, `Is_Active`)
ผู้ดูแลระบบเพิ่มหรือปิดการใช้งานค่าได้เอง โดยเฉพาะ `DEPARTMENT`, `UNIT`, `MEDIA_TYPE` และ `SUB_TYPE`
ที่ให้มาเป็นเพียงตัวอย่าง

- `SUB_TYPE` ใช้ `Parent_Code` เป็น `Budget_Type` — ประเภทย่อยจะถูกกรองตามประเภทงบอัตโนมัติ
- `ACTIVITY_TYPE` ใช้ `Parent_Code` เป็นรหัสโมดูล (`M1`, `M2`, …) โมดูลใหม่เพิ่มประเภทกิจกรรมของตัวเองได้ที่นี่

**ชีต `Status_Master`** เก็บสถานะงานทั้งหมดของทุกโมดูลและเส้นทางที่ไปต่อได้ (`Allowed_Next`)

> หลังแก้ชีต Config ให้ผู้ดูแลระบบกดล้าง cache (เมนู `api_clearCache` ผ่านผู้ใช้บทบาท ADMIN)
> หรือรอไม่เกิน 10 นาที

## 8. กฎสำคัญที่ระบบบังคับ

**ใบเสนอราคาที่ "ใช้ได้" ต้องครบทุกข้อ**

1. แถวผู้ขายในงานยังไม่ถูกลบ
2. สถานะการตอบกลับเป็น `QUOTED`
3. สถานะการตรวจคุณสมบัติไม่ใช่ `FAILED`
4. วันยืนราคาว่างไว้ หรือยังไม่ถึงกำหนด
5. ผู้ขายในทะเบียนไม่ได้อยู่ใน `BLACKLIST`
6. ถ้า `REQUIRE_ALL_ITEMS_PRICED = TRUE` ต้องเสนอราคาครบทุกรายการที่ยังไม่ถูกลบ

**การตัดสิน**

- ใบที่ใช้ได้ ≥ `MIN_QUOTES` → ปิดขั้นตอนหา Vendor ได้
- ใบที่ใช้ได้ < `MIN_QUOTES` → ต้องมีคำขอยกเว้นที่หัวหน้าฝ่ายจัดซื้อ **อนุมัติแล้ว**
- **ใบที่ใช้ได้ = 0 → ปิดไม่ได้ทุกกรณี** แม้มีคำขอยกเว้นที่อนุมัติแล้ว เพราะไม่มีอะไรให้เปรียบเทียบ
- หัวหน้าฝ่ายจัดซื้ออนุมัติคำขอยกเว้นของงานที่ตัวเองเป็นเจ้าของ **ไม่ได้**

**ย้อนสถานะอัตโนมัติ** — หลังทุกการเขียนที่อาจเปลี่ยนคำตอบ (และในงานรายวันสำหรับใบเสนอราคาที่หมดอายุ
โดยไม่มีใครแตะ) ถ้างานที่อยู่ในสถานะ `SOURCING_DONE` ไม่ผ่านกฎอีกต่อไป ระบบจะย้อนกลับเป็น `SOURCING`
บันทึก Change_Log ในชื่อ `SYSTEM` และส่งอีเมลแจ้งเจ้าของงาน

**การตรวจข้อมูลซ้ำ**

| กรณี | ผลลัพธ์ |
|---|---|
| Tax_ID ซ้ำในทะเบียนผู้ขาย | **บล็อก** พร้อมบอกว่าเป็นผู้ขายรายใด |
| เบอร์โทร / อีเมล / ที่อยู่ ตรงกับผู้ขายรายอื่น | **เตือน** (สัญญาณการสมยอมราคา) แต่บันทึกได้ |
| เพิ่มผู้ขายรายเดิมเข้างานซ้ำ | **บล็อก** |
| เพิ่มผู้ขายที่อยู่ใน BLACKLIST เข้างาน | **บล็อก** |
| เปิดงานใหม่ที่เอกสารอ้างอิงหรือป้ายซ้ำกับงานที่ยังเปิดอยู่ | **เตือน** |
| ผู้ขายเสนอราคาด้วยหน่วยที่ต่างจากที่ระบุในงาน | **เตือน** |
| เลข PR ซ้ำกับงานอื่น | **บล็อก** |

**ต้องระบุเหตุผลเสมอเมื่อ** แก้ราคาที่บันทึกไว้แล้ว, เปลี่ยนสถานะการตอบกลับของผู้ขาย, ลบข้อมูลใดๆ,
ย้อนสถานะ, ยกเลิกงาน, โอนงาน, ขอ/พิจารณายกเว้น และ Reopen

**การแก้ไขพร้อมกัน** — ทุกการบันทึกส่งเลขเวอร์ชันของข้อมูลกลับมาด้วย ถ้าไม่ตรงกับในชีต
ระบบจะตอบ `CONFLICT` และไม่เขียนทับงานของคนที่บันทึกไปก่อน

## 9. การทดสอบ

ชุดทดสอบไฟล์เดียว (`tests/Tests.js`) รันได้สองที่ และครอบคลุม Acceptance Test ทั้ง 18 ข้อใน SPEC §13

```bash
npm test                       # รันทั้งหมดบน Node (ไม่ต้องมีบัญชี Google)
node tests/node/run.js --case 18   # รันเฉพาะ Acceptance Test ข้อ 18
node tests/node/run.js --grep quote
npm run check                  # ตรวจ syntax ทุกไฟล์ใน src/server
```

`tests/node/run.js` โหลดไฟล์ทุกไฟล์ใน `src/server` เข้า **vm context เดียวกัน** ซึ่งเลียนแบบ
global scope ของ Apps Script ตรงๆ โค้ดที่ถูกทดสอบจึงเป็นโค้ดชุดเดียวกับที่ deploy จริง
โดยไม่ต้องมี `require`/`module.exports` ในโค้ดฝั่ง server เลย

ตัวรันจงใจโหลดไฟล์ **เรียงตามตัวอักษร** ซึ่งเป็นลำดับที่แย่ที่สุดที่โค้ดชุดนี้น่าจะเจอบน Apps Script
(`Rules.js` มาก่อน `StatusEngine.js`, `Api.js` มาก่อนทุกอย่างที่มันเรียก) โมดูลที่เผลอเรียกโมดูลอื่น
ตอนโหลดไฟล์จึงพังในเทสต์ แทนที่จะไปพังบน production ที่มันจะทำให้ทั้งสคริปต์โหลดไม่ผ่าน

**ทดสอบบน Google จริง** — หลัง `clasp push` ให้รัน `verifyDeployment()` ก่อน แล้วตามด้วย `runAllTests()`
จาก Apps Script editor เพื่อยืนยันสิ่งที่ mock ตรวจแทนไม่ได้ (quota, การ escape ของ HtmlService,
สิทธิ์ Drive, การส่งอีเมลจริง) การทดสอบจะสร้างไฟล์ Google Sheets ชั่วคราวสำหรับแต่ละเคสแล้วย้ายลงถังขยะให้เอง

จากนั้นทดลองใช้กับงานจริงตาม [`docs/UAT.md`](docs/UAT.md) ก่อนเปิดให้ทั้งฝ่ายใช้

## 10. การสำรองข้อมูล

ข้อมูลทั้งหมดอยู่ในไฟล์ Google Sheets ไฟล์เดียว

- **อัตโนมัติ** — Google Sheets เก็บ version history ย้อนหลังให้อยู่แล้ว (`File` → `Version history`)
- **รายเดือน (แนะนำ)** — `File` → `Make a copy` เก็บไว้ในโฟลเดอร์สำรอง หรือดาวน์โหลดเป็น `.xlsx`
- **ก่อนแก้ Schema ครั้งใหญ่** — สำเนาไฟล์ DB ไว้ก่อนรัน `setup()` ทุกครั้ง
- **ห้ามใส่สูตรในชีต DB** ระบบอ่านค่าดิบเท่านั้น สูตรจะทำให้ข้อมูลเพี้ยนและ Looker Studio ต่อยาก
- **ห้ามลบแถว** ระบบใช้ soft delete (`Is_Deleted = TRUE`) ทั้งหมด การลบแถวจริงจะทำให้ประวัติขาด

### ขนาดข้อมูลและประสิทธิภาพ

หน้ารายละเอียดงานอ่านเฉพาะแถวของงานนั้น (ค้นด้วย `TextFinder` บนคอลัมน์ `Case_ID` แล้วอ่านเฉพาะช่วงแถวที่เจอ)
จึงไม่ช้าลงตามขนาดฐานข้อมูล

หน้ารายการงานและภาพรวมทีมต้องรวมยอดข้ามหลายงาน จึงอ่านทั้งชีต `Case_Vendors`, `Case_Items` และ `Quote_Lines`
อย่างละครั้ง เมื่อ `Quote_Lines` เกิน 60,000 แถว ระบบจะ**เลิกใช้เงื่อนไข "เสนอราคาครบทุกรายการ"
เฉพาะในป้ายบนหน้ารายการ** แล้วแสดงเครื่องหมาย `≈` กำกับไว้ เพื่อไม่ให้คำขอเดียวอ่านข้อมูลหลายแสนเซลล์
จนชนเพดานเวลาของ Apps Script

**ตัวเลขที่ใช้ตัดสินใจไม่เคยเป็นค่าประมาณ** — หน้ารายละเอียดงานและการตรวจก่อนเปลี่ยนสถานะ
คำนวณกฎเต็มรูปแบบกับงานทีละงานเสมอ ปรับค่าเพดานนี้ได้ที่ `LIST_SUMMARY_MAX_QUOTE_ROWS` ใน `Rules.js`

## 11. PDPA — ข้อมูลส่วนบุคคล

ชีต `Vendors` เก็บ `Contact_Name`, `Contact_Phone`, `Contact_Email` และ `Address` ซึ่งเป็น
**ข้อมูลส่วนบุคคล** เก็บไว้เพื่อวัตถุประสงค์การจัดซื้อจัดจ้างเท่านั้น ระบบจึง:

- ไม่ส่งข้อมูลผู้ติดต่อออกไปในอีเมลแจ้งเตือนใดๆ (มีชุดทดสอบตรวจข้อนี้โดยเฉพาะ)
- ไม่แชร์ไฟล์ DB ให้ผู้ใช้ทั่วไป — เข้าถึงได้ผ่านหน้าเว็บที่ตรวจสิทธิ์แล้วเท่านั้น
- ตั้งค่าแชร์ไฟล์แนบใน Drive ให้เห็นได้เฉพาะภายในโดเมนของบริษัท

ผู้ดูแลระบบควรทบทวนรายชื่อในชีต `Users` เป็นระยะ และตั้ง `Is_Active = FALSE` สำหรับผู้ที่ไม่ได้ทำงานแล้ว

### หลักการที่ยึดตลอด

1. **Case เป็นแกนกลาง** — ทุกอย่างผูกด้วย `Case_ID` ที่ระบบออกเอง ไม่ใช้เลข PR เป็นตัวตั้ง
   เพราะ PR เกิดขึ้นหลังเลือกผู้ขายได้แล้ว
2. **ไม่เก็บค่าที่คำนวณได้** — ยอดรวมทุกชนิดคำนวณจาก `จำนวน × ราคาต่อหน่วย` ตอนแสดงผล
3. **Soft delete เท่านั้น** — ไม่มีโค้ดส่วนใดลบแถวจริง
4. **อ้างอิงด้วย ID และชื่อคอลัมน์เสมอ** — ไม่ใช้เลขแถวหรือ index ตายตัว คอลัมน์ที่เพิ่มทีหลังจึงไม่ทำให้อะไรพัง
5. **ตรวจสิทธิ์ที่ server ทุกครั้ง** — การซ่อนปุ่มฝั่ง client เป็นความสะดวก ไม่ใช่การควบคุม
6. **ห้ามโมดูลเรียกหากันตอนโหลดไฟล์** — Apps Script เป็นผู้กำหนดลำดับการประมวลผลไฟล์เอง
   โค้ดที่เรียกโมดูลอื่นตอนโหลดจึงทำงานได้ด้วยความบังเอิญ และวันที่ลำดับเปลี่ยน สคริปต์จะโหลด
   ไม่ผ่านทั้งโปรเจกต์ (ไม่ใช่แค่ฟีเจอร์เดียวเสีย) ทุกโมดูลจึงลงทะเบียนตัวเองผ่าน `install()`
   ที่ `Bootstrap.js` เรียกตอน runtime และ test harness ก็จงใจโหลดไฟล์แบบเรียงตามตัวอักษร
   เพื่อให้ความผิดพลาดแบบนี้โผล่ในเทสต์ ไม่ใช่บน production

| สิ่งที่ต้องทำ | วิธี |
|---|---|
| เพิ่มตารางหรือคอลัมน์ | เพิ่ม entry ใน `Schema.js` แล้วรัน `setup()` ซ้ำ — คอลัมน์ใหม่จะถูกเพิ่มต่อท้าย ข้อมูลเดิมไม่เสีย |
| เปิดใช้สถานะของโมดูลใหม่ | กรอก `Allowed_Next` ในชีต `Status_Master` (แถวของทุกโมดูลมีอยู่แล้ว) เช่น เพิ่ม `PRICE_RESEARCH` ลงใน `Allowed_Next` ของ `SOURCING_DONE` |

| เพิ่มเงื่อนไขย้อนสถานะอัตโนมัติ | `StatusEngine.registerRecheck(MyRules.recheck)` ภายใน `install()` เดียวกัน |
| เพิ่มประเภทกิจกรรมของโมดูล | เพิ่มแถวใน `Config_Lists` ที่ `List_Name = ACTIVITY_TYPE` และ `Parent_Code = M2` |
| เพิ่มแท็บในหน้ารายละเอียดงาน | สร้างไฟล์ `src/client/views/CaseBenchmark.html` เรียก `App.registerCaseTab({...})` แล้ว `include` ใน `Index.html` และเพิ่มชื่อไฟล์ใน `Verify.HTML_FILES` |
| เพิ่มปุ่มบนหัวหน้ารายละเอียดงาน | `App.registerCaseHeaderAction({...})` |

ตาราง `Benchmarks` และคอลัมน์ที่ทำเครื่องหมาย `[RESERVED]` (เช่น `Final_Unit_Price`,
`Qualification_Status`, `Is_Selected`, `Directors`, `Selected_Vendor_ID`) ถูกสร้างไว้ในชีตแล้ว
แต่ยังไม่มีหน้าจอใดเขียนลงไป

## 15. ข้อสมมติที่ควรยืนยันกับผู้ใช้งานจริง

ทั้งหมดนี้ทำให้เปลี่ยนได้ง่ายแล้ว
